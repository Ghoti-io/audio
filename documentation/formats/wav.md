# WAV {#format_wav}

RIFF/WAVE, plus RF64 and BW64. Little-endian throughout.

## What is implemented

**Read.** `WAVE_FORMAT_PCM` at 8, 16, 24 and 32 bits, `WAVE_FORMAT_IEEE_FLOAT`
at 32 and 64, and `WAVE_FORMAT_EXTENSIBLE` wrapping either. The `fmt ` and
`data` chunks; anything else is skipped by its stated length. **RF64 and
BW64**: the `ds64` chunk is consulted before any size is believed, so a
`data` length of `0xFFFFFFFF` resolves to the 64-bit value rather than being
read as four gigabytes.

**Write.** The same formats, except signed 8-bit, which the container cannot
express. `WAVE_FORMAT_EXTENSIBLE` is emitted when and only when it says
something the plain header cannot - more than two channels, or a channel mask
worth stating - because every reader accepts the plain form and some old ones
do not accept the other.

## Things that are easy to get wrong, and what this does

**8-bit WAV is unsigned.** Silence is 128, not 0. AIFF's 8-bit is signed, and
the two formats genuinely disagree; ::GAUD_SAMPLE_U8 and ::GAUD_SAMPLE_S8
carry the difference rather than a bit count plus a flag somebody forgets to
set. A signed 8-bit track is **refused** by this writer rather than being
written as unsigned with every sample shifted by 128 unannounced.

**RF64 is not exotic.** Any recorder writing more than 4 GiB emits it, and a
reader that knows only plain RIFF reports a 32-bit size that is simply wrong
rather than failing. It is the same parser with one chunk consulted first.

**"RIFF" does not mean audio.** AVI is a RIFF file, and so are several
others. This codec's probe requires the `WAVE` form type at offset 8 and
answers no otherwise - and because a probe's answer *replaces* what its
signatures said rather than being the larger of the two, that no is
effective.

**A `data` chunk can claim more than the file holds.** A truncated download
states the length it was going to have. The claim is clamped to what is
actually present and a diagnostic says so, because a decoder that believed it
would hand back whatever followed in memory.

**The pad byte.** A chunk of odd length is followed by one pad byte which is
counted in the RIFF size and not in the chunk's own. Written, and not counted
as a sample on the way back in.

## Not implemented

- Writing RF64. Past 4 GiB the writer returns ::GAUD_ERR_UNSUPPORTED rather
  than truncating a 32-bit length into a file that opens and is wrong.
- Any compressed `WAVE_FORMAT_*`: µ-law, A-law, ADPCM, GSM and the rest.
  Phase 2 brings them. They are refused by format tag, not misread as PCM.
- `cue `, `LIST`/`INFO`, `bext` and the other metadata chunks - phase 3. They
  are skipped by length today, so they do not prevent a file from loading.

## Specification

There is no single authoritative document. The Microsoft/IBM Multimedia
Programming Interface and Data Specifications 1.0 defines RIFF and the
original `WAVE` chunks; `WAVEFORMATEXTENSIBLE` is Microsoft's later
extension; RF64 is EBU Tech 3306 and BW64 is ITU-R BS.2088, which are the
same arrangement under two names.

## How it is checked

Fixtures generated by ffmpeg and sox, never by this library. `make
check-corpus` requires ffmpeg, sox, libsndfile and Python's `wave` to decode
each one exactly as this does; `make check-writer` requires them to read what
this writes; `make check-golden` requires the samples to be identical on
big-endian targets, which is where this codec's byte-swapping actually runs.
